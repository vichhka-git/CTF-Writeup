# VaultKeeper

**Category:** Mobile · **Points:** 120 · **Flag:** `CSCTF{intent_uri_and_a_broadcast_unlock_the_vault}`

## What the handout gives you

The handout provides an Android application package and an operational authorization code from a field handover card.

- `vaultkeeper.apk` — 2,413,853 bytes, Android application package containing Dalvik bytecode, manifest, and resources.
- `ZHUU-SANS-9XJN-QPCQ` — 19-character authorization string provided in the challenge prompt.

## Walkthrough

1. **Decompile the package.** Extract Dalvik bytecode and resources using JADX:
   `jadx -d out vaultkeeper.apk`
   Review `AndroidManifest.xml` to identify the declared components: `MainActivity`, `ArchiveActivity`, `LegacyRecoveryActivity`, `RecoveryDiagnosticsActivity`, and `RecoveryStage2Receiver`.

2. **Locate the decryption logic.** Inspect `MainActivity.java`. The locked vault text corresponds to resource `R.string.flag_ciphertext_b64`. Decryption uses `AES/GCM/NoPadding`. The first 12 bytes of the Base64-decoded string serve as the GCM initialization vector, and the remaining bytes contain the ciphertext and 16-byte authentication tag.

3. **Trace the AES key construction.** `MainActivity` constructs the 256-bit AES key by hashing three concatenated strings with SHA-256:
   - `strA0`: generated by static helper `A.c.a0(context)`.
   - `string`: read from SharedPreferences key `archive_digits_cache`.
   - `string2`: the text entered into the authorization input field, supplied as `ZHUU-SANS-9XJN-QPCQ`.

4. **Derive the certificate recovery string.** Examine `A.c.a0(context)` in `A/c.java`. The function reads the first package signature from `PackageManager`, computes its SHA-256 digest, takes the first 8 hexadecimal characters in uppercase, and prefixes the result with `KJSC-` and suffixes it with `-RECOVERY`. Extracting the certificate from the APK signing block and hashing its DER bytes yields prefix `1C28DC7E`. The resulting value is `KJSC-1C28DC7E-RECOVERY`.

5. **Recover the archive digits.** Check `ArchiveActivity.java` and `RecoveryStage2Receiver.java`. In `ArchiveActivity`, entering a 4-digit code calculates an HMAC-SHA256 digest using the key from `R.string.archive_session` (`VK-7F42`). The first 8 hexadecimal characters of the digest form `archive_key`. `RecoveryStage2Receiver` accepts stage 2 only when `archive_key` equals `3778F16D`. Testing four-digit numbers from 0000 to 9999 shows that `4972` produces the prefix `3778F16D`. The application saves this string into `archive_digits_cache`.

6. **Decrypt the flag.** Concatenate the three components in order: `KJSC-1C28DC7E-RECOVERY` + `4972` + `ZHUU-SANS-9XJN-QPCQ`. Compute the SHA-256 digest of the combined UTF-8 bytes to obtain the 32-byte AES key. Initialize AES-GCM with this key and the 12-byte IV to decrypt the ciphertext.

## Answer

Decrypting the ciphertext produces the plaintext recovery note:

`CSCTF{intent_uri_and_a_broadcast_unlock_the_vault}`

## Notes

The application implements a multi-stage UI unlock workflow: dispatching an intent to `RecoveryDiagnosticsActivity` with URI `vault://recover?stage=1` marks stage 1 complete, and broadcasting `archive_key` to `RecoveryStage2Receiver` marks stage 2 complete. Offline static analysis recovers all three key components without running the Android operating system.
