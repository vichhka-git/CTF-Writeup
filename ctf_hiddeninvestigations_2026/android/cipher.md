# Cipher

Android, 61 points, 261 solves. The APK is a one-screen vault that asks for a passphrase and then decrypts 64 records. The passphrase is not stored anywhere. It is generated by legacy classes that the current interface no longer calls, from an 18-bit seed, and the APK carries everything required to test candidates offline.

## What you are given

`cipher.zip` contains `cipher.apk` (38,969 bytes, sha256 `d32ec3f2c705e1aefcba505d5f3af157680fe0bab50bc69418927c9298126745`). There is no device image and no live service. The whole solve is static.

Unpacking shows package `com.hictf26.cipher`, six DEX files (`classes.dex` to `classes6.dex`), no native libraries and no assets directory. The three raw resources are `res/raw/m4.bin` (2048 bytes), `res/raw/n3.bin` (96 bytes) and `res/raw/p7.bin` (6101 bytes). Decompiling with jadx 1.5.6 yields 13 application classes.

## Reproduction

1. Read `MainActivity`. The button listener reads the typed passphrase, calls `CryptoEngine.deriveRoot(password, store.getSalt())`, then `CryptoEngine.verify(context, root)`, and on success `CryptoEngine.decryptAll(root, salt, records)`. No other check gates the vault, so the verifier is the target.

2. Read `data/VaultStore` to learn the container at `res/raw/p7.bin`:

```
0    4 bytes   "V1LT"
4    1 byte    version, must be 3
5    16 bytes  salt
21   1 byte    record count, 0x40 = 64
then per record: 1 byte index, 12 byte nonce, 2 byte big-endian length, ciphertext
```

The 16 bytes at offset 5 are the salt used by the KDF.

3. Read `crypto/CryptoEngine`, `crypto/Hkdf`, `crypto/AnchorReader` and `crypto/Names`. The provider names are stored encoded and decode to `PBKDF2WithHmacSHA256`, `HmacSHA256`, `AES` and `AES/GCM/NoPadding`. The parameters are:

```
root        = PBKDF2-HMAC-SHA256(passphrase, salt, 32768, 32)
verifier    = HMAC-SHA256(root, "cipher-verifier-v3")[:16]
expected[i] = n3[(11*i + 7) % 96] ^ ((19*i + 167) & 255)     i = 0..15
subkey      = HKDF-SHA256(root, salt, info = b"v1" + index)
plaintext   = AES-256-GCM(subkey, nonce, AAD = b"V1LT" + index)
```

Evaluated against `n3.bin`, the 16 expected bytes are `f3840a2b902c711f0ac8f924c295e815`. Each plaintext is `title \x1f secret` in UTF-8.

4. Find the passphrase generator. `MainActivity` never references it, but the APK still ships the `legacy` package. `SeedWindow.base()` mixes compile-time constants into a 12-bit bucket and shifts it left by `bits()`, which is 18; `span()` is `1 << 18`. For this build the window is `764149760` to `764411903`, 262,144 values.

5. Read `legacy/LegacyPassphrase` and `legacy/Lexicon`. The generator seeds `java.util.Random(7640891576956012809L ^ seed)`, draws six words with `nextInt(256)` from a 256-entry lexicon, joins them with hyphens, and appends `(nextInt(100) + 7 * bitCount(seed)) % 100` as two digits. `m4.bin` decodes to the lexicon by XORing each byte with `(((i * 73) + 93) ^ ((i >>> 3) * 17)) & 255` and cutting the result into 8-byte words.

The generator must be Java's, not Python's. `nextInt(256)` takes the power-of-two path, and a JVM or a faithful reimplementation of `java.util.Random` is needed for the words to line up.

6. Sweep the window. Each candidate costs one 32,768-iteration PBKDF2 and one HMAC, and the 16-byte comparison rejects almost everything. Seed `764408707` is the single hit:

```
seed       764408707
passphrase smxvoisk-fcxfgnpl-poznukfv-zxpmztpo-yanlxwmm-yanlxwmm-42
root       2803a69149bea3d3535a6ae6073cfb21c76f5ddeebcf7e6b719cbbd3ffb47879
```

The passphrase shape is a useful sanity check: six eight-letter pseudo-words built from a 256-word dictionary, one of them repeated, then a two-digit tail that is a function of the seed.

7. Decrypt all 64 records. Each record has its own HKDF subkey and its own nonce, and AES-GCM authenticates every one, so a wrong root fails the first tag instead of producing noise. Record 47 decrypts to title `Archived security memo` and secret `hiCTF{cryptography_should_be_implemnetd_properly}`. The typo in `implemnetd` is inside the plaintext, not in the transcription.

8. Cross-check before trusting the extraction. The workspace keeps a second implementation in `jcheck/Verify.java` that uses only the JDK `SecretKeyFactory`, `Mac` and `AES/GCM` against the same three resource files. It reproduces the same seed, passphrase, root hex, `verifier_ok=true` and the same record 47 plaintext.

The notes record the seed, passphrase and root. They do not record the 64 nonces or the ciphertext contents, which stay in the store.

## Why it works

The passphrase is derived from a deterministic generator over a seed space of 2^18 values. That is small enough to enumerate, and the author left the classes that define both halves of it, the seed window and the word generator, inside the shipped APK. The verifier anchor is also local, in `n3.bin`, so a candidate can be checked with no device and no network.

The PBKDF2 work factor is the only cost, and it protects a 32-byte root that the attacker can compute as fast as the app can. A 32,768-iteration KDF is meaningless against a 262,144-entry seed space, which is what the flag text is pointing at.
